# Qwen3.8-27B Q8_0 CLI run on gfx906

One run per setting on two 32 GiB MI60 cards (gfx906), TheRock ROCm 10.2.0, using `build-ilp/bin/llama-cli` from mx-llama.cpp build 11776 / commit `766f7c5e0`. The target was the cached Unsloth Qwen3.8-27B Q8_0 model with the cached z-lab DFlash2 draft where noted. This is the 27B model, not Flash Next.

The run uses the repository's `flake.nix` as the prompt, `-n 4000`, context capacity `100096`, greedy sampling, 2048 batch and ubatch, flash attention, tensor parallel across both GPUs, and a 50/50 split. Context capacity meets the 100K target; these runs used about 6K prompt-plus-output tokens, so they do not measure a full 100K prompt.

| Draft setting | PP (tok/s) | TG (tok/s) |
| --- | ---: | ---: |
| DFlash, max draft 7 | 543.7 | 59.9 |
| MTP depth 2 | 549.7 | 56.8 |
| MTP depth 3 | 545.2 | 60.0 |

These are single runs, so the 0.1 tok/s TG difference between DFlash and MTP3 is noise-sized. MTP2 had the highest measured PP; MTP3 and DFlash were effectively tied for TG. Use MTP2 when prompt processing is the priority and MTP3 or DFlash when generation is the priority, pending repeated runs.

## Reproduction commands

```sh
source /home/raistlin/amd-clean/env/therock.sh
LLAMA=/home/raistlin/infer/mx-llama.cpp/build-ilp/bin/llama-cli
MODEL=/home/raistlin/.cache/huggingface/hub/models--unsloth--Qwen3.8-27B-GGUF/snapshots/4ca720788d1e01f1bff70c033e0d0028fd02e502/Qwen3.8-27B-Q8_0.gguf
COMMON=(-m "$MODEL" --offline -ngl 999 -dev ROCm0,ROCm1 -sm tensor -fa on \
  -b 2048 -ub 2048 -c 100096 --temp 0 --top-k 1 -s 42 \
  -f /home/raistlin/infer/mx-llama.cpp/flake.nix -n 4000)

"$LLAMA" "${COMMON[@]}" \
  --spec-type draft-dflash --spec-draft-n-max 7 \
  --spec-draft-hf z-lab/Qwen3.8-27B-DFlash2-GGUF:Q8_0 \
  --spec-draft-model Qwen3.8-27B-DFlash2-Q8_0.gguf

"$LLAMA" "${COMMON[@]}" \
  --spec-type draft-mtp --spec-draft-n-max 2 --spec-draft-backend-sampling

"$LLAMA" "${COMMON[@]}" \
  --spec-type draft-mtp --spec-draft-n-max 3 --spec-draft-backend-sampling
```

The earlier 865 MiB ROCm0 allocation failure did not recur with Strata stopped. At the last measured Strata server state, it occupied 31.2 GB on GPU0 and 25.7 GB on GPU1, leaving about 1.6 GiB free on GPU0. This makes VRAM competition with the still-running Strata server the likely cause; the clean-GPU retry is evidence, but not a reproduction of the failed state.

The server's 100096 context setting is a configured capacity, not a measured maximum. The separate Flash Next quant, VRAM headroom and context-allocation findings are in [the Flash Next gfx906 report](2026-10-25-qwen3.8-flash-next-gfx906.md).
