# Roofline: Qwen3.8-27B on two gfx906 GPUs (TP)

Historical record. Earlier recommendations and task deadlines describe the recorded tree; use the [current vr guide](../../../README.md) for operating instructions. Exact pre-cleanup bytes are preserved in `before-cleanup.tar.gz`.

Date: 2026-10-12. State: working tree after the [2026-10-12 follow-up changes](2026-10-12-tp-profile-findings.md#results-of-the-follow-up-changes-2026-10-12-uncommitted). No new runs for this note; it uses the profiles and benchmarks in that document.

Short answer: the raw model has modest TG headroom (realistically +15-20%, spread over several hard items) and larger PP headroom (up to about +35%, almost all from hiding AllReduce traffic). For TG, speculative decoding (MTP/DFlash) is the better next step. Speculation does not help PP.

## Assumptions

- Weights: 27.04 GiB Q8_0 total, about 14.5 GB read per GPU per token with `-ts 50/50`.
- HBM2 peak 1024 GB/s per GPU. Practical read ceiling assumed about 850 GB/s. **Not measured on this box**; a plain read kernel would confirm it.
- Int8 dot-product peak (`v_dot4_i32_i8`, 8 ops per lane per clock): MI60 64 CU at 1.8 GHz is about 59 TOPS; the MI50 (Pro VII VBIOS, 170 W cap) 60 CU at about 1.7 GHz is about 53 TOPS. One token is about 54.6 G int8 ops (2 x 27.3e9).
- Host links: Gen3 x8 (ROCm0) and Gen4 x4 behind DMI (ROCm1), about 6.5-7 GB/s per direction each. No P2P.

## TG (bandwidth bound)

| | Per token | t/s |
| --- | ---: | ---: |
| Weights at 1024 GB/s (hard floor) | 14.2 ms | about 70 |
| Weights at about 850 GB/s (practical floor) | 17.1 ms | about 58 |
| Now (llama-bench TG128) | 27.2 ms | 36.8 |

Gap to the practical floor, slower GPU (ROCm1), per token:

| Component | Now | Realistic saving | Notes |
| --- | ---: | ---: | --- |
| Repacked Q8_0 mat-vec at about 715-745 GB/s | about 19 ms | 2-2.5 ms | Kernel already well tuned; remaining loss is occupancy, tail and per-wave latency |
| About 1100 small kernels (norms, GDN, rope, get_rows, conv, quantize) | about 6-7 ms | 2-3 ms | Each fusion is worth 1-3% |
| Host gap before each token-graph launch | about 1.5-2 ms | 1-1.5 ms | Not yet diagnosed |
| AllReduce, 128 per token at about 12 us | about 1.5 ms | about 0.5 ms | Near the PCIe round-trip floor |

Realistic raw target: about 42-45 t/s (+15-20%). Reaching the 58 t/s floor would need all non-weight work to disappear, which is not plausible.

## PP (compute bound, plus PCIe)

| | Per 2048-token ubatch | t/s |
| --- | ---: | ---: |
| Int8 peak, both GPUs (about 112 TOPS) | about 1.0 s | about 2000 |
| GEMM at the measured 56% of peak | about 1.9 s | about 1100 |
| GEMM + other kernels, comm fully hidden | about 2.3 s | about 890 |
| Now (llama-bench PP2048) | 3.16 s | 649 |

- The GEMM itself is near the practical limit for these cards (about 56% of dp4a peak on the MI60).
- AllReduce moves about 2.7 GB per direction per GPU per ubatch (127 AllReduces of 2048 x 5120 BF16). At about 7 GB/s that is at least 0.4 s even with the new full-duplex copies. It can only be hidden (overlap with compute) or shrunk (lossy FP8/INT8 wire).
- Hiding it means pipelining token slabs: the AllReduce of slab k overlaps the GEMM of slab k+1. This is the one remaining large raw PP item (up to about +35%) and touches the TP scheduler; discuss the design first.
- Other kernels: chunked GDN about 6% of the ubatch; the remainder is small.

## Lower-bit weights (Q6_K, Q5_K, Q4_K)

Bits per weight: Q8_0 8.5, Q6_K 6.56, Q5_K 5.5, Q4_K 4.5. Only the mat-vec part of TG (about 19 of 27.2 ms) scales with weight bytes; the about 8 ms of small kernels, AllReduce and host gap does not.

TG estimate if the mat-vec kept the Q8_0 bandwidth efficiency (best case):

| Quant | Bytes vs Q8_0 | Mat-vec | Total | TG | Break-even mat-vec bandwidth |
| --- | ---: | ---: | ---: | ---: | ---: |
| Q8_0 | 1.00 | 19.0 ms | 27.2 ms | 36.8 | 740 GB/s |
| Q6_K | 0.77 | 14.7 ms | 22.9 ms | about 44 (+19%) | 570 GB/s |
| Q5_K | 0.65 | 12.3 ms | 20.5 ms | about 49 (+33%) | 480 GB/s |
| Q4_K | 0.53 | 10.1 ms | 18.3 ms | about 55 (+48%) | 390 GB/s |

"Break-even" is the effective weight bandwidth at which the lower-bit mat-vec only matches Q8_0 time. Below it, the smaller file is slower.

Why the K-quant paths are likely below the best case on this fork:

- K-quants are repacked but use the generic `mul_mat_vec_rp`; Q8_0 has its own tuned kernel. K-quant decode (nibble/2-bit planes, sub-block scales) costs more ALU per byte, and gfx906 mat-vec is already latency sensitive.
- Dense gate+up fusion (`ggml_cuda_repack_mmv_fusion_supported`) admits only Q8_0 and MXFP4, so K-quant FFNs pay separate gate, up and GLU launches.
- The 8-row workgroup change applies only to the Q8_0 kernel.
- PP: `mmq-config-gfx906.cuh` tunes Q8_0/MXFP4; other types fall back to the RDNA2 table, and K-quant tiles do more dequant work per int8 MAC. Expect PP at or below Q8_0.

Expected outcome: Q6_K probably lands near its break-even (small or no TG gain, PP loss). Q4_K/Q5_K have enough margin to win on TG even with weaker kernels, at a quality cost and probably a PP loss. MTP/DFlash acceptance can also drop with lower-precision weights.

To decide, one paired run is enough: the same llama-bench command (PP2048 / TG128, `-ts 50/50`) on Q8_0 and on the candidate GGUF, plus one CLI check. No Q4/Q5/Q6 Qwen3.8 file is cached locally (only Q8_0).

## Recommendation

1. TG: move to MTP/DFlash. Re-run the depth sweep on the current build; the best depth may shift now that the base is faster.
2. PP: if prompt speed matters, the slab-overlapped AllReduce is the remaining big raw item.
3. Lower-bit weights: only Q4_K/Q5_K have enough byte savings to beat the weaker kernels on TG. Measure one before investing in K-quant kernel work.

## DFlash2 ceiling for long general generation (Q8_0, 2026-10-12)

Model: TG = L / (verify(k+1) + draft + host gaps + prepare/sampling), L = accepted tokens per step.

Measured inputs (round 2/3): verify GPU time 29.7 ms (1 row), 33.8 (3), 39.6 (6), about 45 (8); DFlash draft about 7 ms GPU per step; host gaps about 10 ms per step; remaining prepare/sampling about 6 ms. On `flake.nix`: L 3.33 at n-max 5 (51-54.5 TG), L 3.86 at n-max 7.

| Case | Step | L | TG |
| --- | ---: | ---: | ---: |
| Now, n-max 5 (measured) | about 62-65 ms | 3.33 | 51-54 |
| Draft captured as one graph (host gaps 10 -> 1 ms) | about 54 ms | 3.33 | about 62 |
| + prepare/sampling 6 -> 2 ms, verify(6) 39.6 -> 36 ms | about 44 ms | 3.33 | about 75 |
| Same, n-max 7 (verify(8) about 42 ms) | about 50 ms | 3.86 | about 77 |
| Same engineering, prose-like content (L 2.5-3.0) | 44-50 ms | 2.5-3.0 | about 55-65 |

Long context costs little on this hybrid model: only 16 of 64 layers keep a KV cache, so at 32k tokens the extra KV read is about 0.5 GB per GPU per pass (about +0.7 ms, 1-2%).

So the realistic DFlash ceiling at Q8_0 is about 70-78 t/s on code/structured output like the flake.nix workload and about 55-65 t/s on general prose, against about 60 for MTP2 today. Gaps, in order of value:

1. Draft step as one replayable graph (about +15%). Blocker: the round-2 content-keyed replay gave wrong drafts; find which draft inputs (positions, inject rows, KV indices) are baked into the captured graph instead of read from fixed buffers.
2. Prepare and sampling overhead per step, about 6 ms -> 2 ms (about +8%).
3. Verify: AllReduce about 5.6 ms per step and remaining small-kernel fusions, about 3-4 ms (about +7%).
4. Prefill tax: DFlash CLI PP 533-548 vs 558 plain; target feature taps during prefill still cost 2-4%.
5. Acceptance is the limit beyond that: L depends on content and on the DFlash2 checkpoint, not on kernels. 85 t/s needs L of about 3.7 or more at a 44 ms step.

### Measured on a general prose prompt (2026-10-12)

Prompt: a long-essay request (printing press, 1450-1700), `-n 512`, greedy, current build. Plain 36.6 t/s; MTP2 + backend sampling 56.5; DFlash n-max 5 59.4 and 60.0 (two runs); DFlash n-max 7 55.8.

DFlash n-max 5 statistics: 134 steps for 512 tokens, mean accepted length 3.81, acceptance by position 0.84, 0.68, 0.53, 0.43, 0.32. Step about 64 ms: draft generation 15.4 ms (`dur g` 2066 ms / 134), prepare 1.3 ms, verify path about 47 ms (verify(6) GPU time is about 39.6 ms, so about 7 ms of host/sampling overhead on the verify path).

Ceiling on this content with the gaps closed: draft 15.4 -> about 5 ms (one replayable graph, no host gaps), verify-path overhead 7 -> about 2 ms, verify(6) 39.6 -> about 36 ms. Step about 44 ms, giving 3.81 / 44 ms = **about 85 t/s**. Prose acceptance here (3.81) is higher than on the flake.nix reasoning output (3.33).

MTP2 is the better general default (1.5x plain, steady). DFlash wins on short-context reasoning and prose (63 math, 60 essay) but loses on long contexts: at 11.8k prompt tokens its draft step costs about 27 ms (15 ms at a short prompt), because the draft attends over all target features and runs tensor-parallel with per-subgraph dispatch.

DFlash ceiling per prompt with the draft at about 5 ms and verify overhead trimmed (step about 44-48 ms): long-doc summary about 63, code review about 75, code generation about 63, math about 90, tutorial about 65, mean about 70 t/s. Gaps in order: (1) draft cost that grows with context (attention over the full feature context, TP split, no graph replay); (2) the per-step host/sampling overhead; (3) verify cost; acceptance (2.9-4.2 here) sets the rest.

The first run of this table exposed a race in the duplex copy-engine AllReduce (non-slab path, 1 MB+ ubatches such as a 237-token prompt tail): the compute stream could reuse the pooled BF16 buffer before its D2H finished, corrupting the AllReduce. It gave NaN MTP drafts and 0% DFlash acceptance on the code-review prompt. Fixed in `allreduce.cu` (`src_read_done` wait).

### DFlash2 faster than MTP2 (2026-10-12, later)

Code changes (all uncommitted, each with a switch):

- Single-GPU DFlash draft for a tensor-parallel target (`common/speculative.cpp`): the draft loads on the first target device automatically (`LLAMA_DFLASH_DRAFT_TP=1` or `-devd` overrides). No AllReduce per draft layer and no meta-backend dispatch.
- Private draft head (`llama_context::load_private_head`, `LLAMA_DFLASH_PRIVATE_HEAD`): the draft cannot read the target's tensor-parallel token embedding and output head, so it loads copies from the target GGUF (path now kept in `llama_model::path`). The output head goes into the draft's repacked buffer type, so the 6-row head mat-vec takes the repacked kernel (head 4.3 -> about 1.6 ms per step).
- Prompt replay: default draft window 4096 rows (`LLAMA_DSPARK_DRAFT_WINDOW`), trimmed inside the oldest kept chunk; lag-one flush every 2048 rows (`LLAMA_DSPARK_FLUSH_ROWS`) on a worker thread (`LLAMA_DFLASH_ASYNC_REPLAY`), so the replay overlaps the target prefill instead of landing in the first draft. Output text is identical to the lazy replay.
- Tried and reverted: keyed multi-graph reuse in `llama_context` (no gain on the single-GPU draft, and it crashed after a compute-buffer reallocation).

### Correctness: how MTP2 and DFlash deviate from plain decoding (2026-10-12)

`llama-server`, `/v1/chat/completions`, greedy, 384 tokens, `top_logprobs` 2, prompts math / code generation / code review.

| Prompt | Mode | First differing token | Plain top-1 vs top-2 margin there (nats) | Speculative picked plain's #2 | Mean abs logprob change before it |
| --- | --- | ---: | ---: | --- | ---: |
| Math | MTP2 | 80 | 0.0054 | yes | 0.0049 |
| Math | DFlash5 | 4 | 0.0039 | yes | 0.0009 |
| Code generation | MTP2 | 97 | 0.0250 | yes | 0.0038 |
| Code generation | DFlash5 | 97 | 0.0250 | yes | 0.0038 |
| Code review | MTP2 | 77 | 0.0028 | yes | 0.0065 |
| Code review | DFlash5 | 4 | 0.0475 | yes | 0.0009 |

Plain's own margin distribution: 1st percentile 0.016-0.035 nats, median 2.4-5.3; 5-8 of 384 tokens per prompt have a margin below 0.05.

Every emitted token in every mode is the argmax of the logprobs the target reported for that position (0 of 1152 per mode are not), and the mean chosen-token logprob is the same within noise (plain -0.3116, MTP2 -0.3114, DFlash5 -0.3151).

Reading: speculative acceptance is exact greedy with respect to the target's verify logits. The only deviation source is the numerics of the batched verify pass (2-8 rows through different kernels than 1-row decode): logprobs move by about 0.001-0.007 nats, which flips the rare near-tie tokens (margin below about 0.05 nats). After the first flip the texts follow different but equally likely paths. No sign of a speculation bug or of a quality loss.
