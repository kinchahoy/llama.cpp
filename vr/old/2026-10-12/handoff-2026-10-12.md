## Plan (in order)

### 0. Baseline (about 10 min)

Run plain, dflash7, dflash5 and mtp3 with `-n 4000` through the script. Record PP, TG and mean accepted length. This also checks whether long generation changes acceptance.

### 1. Make the 2-8 token verify batch cheap (biggest lever; helps DFlash and MTP)

- Profile `llama-bench -p 8 -n 0 -r 3` with `rocprofv3 --kernel-trace --output-format csv`. Compare per-kernel time against `-p 1`. Aggregation scripts: `vr/results/2026-10-12-tp-profile/kernel_summary.py`.
- Narrow-batch repacked mat-vec: `ggml/src/ggml-cuda/q8_repack/mul-mat.cu` line about 76 (`ne11 <= MMQ_RP_Q8_MMV_MAX_TOKENS`) calls `ggml_cuda_mul_mat_repacked_nc_t`, kernel `mul_mat_vec_repacked_nc` in `q8_repack/repack-kernels.cuh` (about line 1136). Check whether each weight is read once for all columns, the workgroup shape (the single-token kernel benefited from 8 rows per workgroup, see `rp_q8_0_mmv_launch`), register use and occupancy. Target: 8-column cost within about 1.3x of 1-column cost.
- Gate+up fusion only fires for `ne[1] == 1` (`ggml_cuda_repack_mmv_fusion_width_ok`, `ggml-cuda.cu` fusion code). At 8 tokens, gate, up and GLU run separately. A 2-8 column fused variant reads the FFN weights once instead of twice.
- Other ops that scale with tokens: flash attention for 8 query rows, GDN (check which path runs for 8 tokens: `gated_delta_net.cu`), `quantize_q8_1`. The fused add+norm+Q8_1 producer (`ggml_cuda_q8_1_producer_target` in `ggml-cuda.cu`) only handles `ne[1] == 1`; extending it to up to 8 rows is easy (the kernel is per row; keep the cache key identical to the consumer's).
- Verify batches are already captured as whole-token graphs (`[meta-prof] replayed tokens=55` in the DFlash run), so launch overhead is not the issue.

### 2. Cut DFlash draft cost (27 ms generate + 17 ms prepare per step)

- The draft runs tensor-parallel across both GPUs because it shares the target output head. `-devd ROCm0` aborts: `pre-allocated tensor (output.weight) in a buffer (Meta(ROCm0,ROCm1)) that cannot run the operation`. Options: (a) mirror the output head for the draft (about 1.35 GB Q8_0) so the draft runs on one GPU without AllReduce; (b) keep TP but make sure the draft's graphs are captured and replayed (check `GGML_META_PROFILE` lines for the draft context: per-call `close` of 40 ms suggests per-subgraph dispatch with host waits). Code: `common/speculative.cpp` (DFlash path, timers around lines 209, 1290, 1520), `src/llama-context.cpp`, `src/llama-model.cpp` (output head sharing).
- Find the unattributed about 1 s in `dur p`: add timers or read the code path between the listed phases.

### 3. Recover prefill with DFlash on

Prompt phase costs: inject 677 ms, tgtsync 213 ms, gather 130 ms for a 2086-row prompt. The draft's prompt injection likely runs through the same slow TP draft path; fixing step 2 may fix most of it. Also check whether target feature capture during prefill forces synchronization (`tgtsync`) that blocks the slab-overlapped AllReduce.

### 4. Tune

`--spec-draft-n-max` 4 to 8 once steps 1-2 land (the optimum moves when verify gets cheap). Compare MTP depth 3-4 too; MTP pays sequential draft steps (about 2-4 ms each) but has a smaller prefill cost.

## Theory to keep in mind

speedup = L x T1 / (Tverify(k+1) + Tdraft + Tprep), T1 = 27 ms. With L = 3.9, 85 t/s needs a step of about 46 ms in total. Every millisecond removed from verify, draft or prepare is worth the same. If acceptance on the 4000-token run is lower than 3.9, 85 needs a proportionally faster step; report that clearly.
